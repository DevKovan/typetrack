Notes on what's happening above, per scenario:
- Scenario 1: `versionMiddleware` injects `appVersion`/`buildId` into
  `event.metadata` (basic usage). `enrichmentMiddleware` (registered before
  `redactMiddleware`) derives `emailDomain` from the still-unredacted `email`,
  then `redactMiddleware` replaces `email`'s value with `"[REDACTED]"` --
  composition, in the order that keeps `emailDomain` correct. `loggingMiddleware`
  and the two `trace:*` tracer middlewares show the literal before(all)
  -> dispatch -> after(all) sequence: every `[before]`/"typetrack: [before]"
  line appears before the provider's "received" line, and every `[after]`/
  "typetrack: [after]" line appears after it -- never interleaved with
  dispatch itself.
- Scenario 2: the exact same event, through a pipeline differing only in
  swapping `enrichmentMiddleware` and `redactMiddleware`'s registration order
  (`redactMiddleware` first). By the time enrichment's function runs, `email`
  is already `"[REDACTED]"` (no `@`), so `emailDomain` falls back to
  `"unknown"` instead of `"example.com"` -- the exact same input event
  produces different delivered data purely because of registration order.
- Scenario 3: `"Purchase Completed"` is tracked with an invalid `value`
  (`-50`). `order-value-guard`'s `before()` throws; per the locked fan-out
  rule, only middlewares that already ran (`logging`, `trace:start`, and
  `order-value-guard` itself, in that registration order) are notified --
  `loggingMiddleware`'s `onError` fires with `source: "middleware"` (no
  `providerName`). Neither `trace:end` nor the provider ever see this event:
  no "[before] trace:end", no "[provider] ... received", no "[after] ..." at
  all for this call -- the chain stopped dead at the throwing middleware.
- Scenario 4: `"Payment Method Charged"` passes every `before()` (its `value`
  is valid), so the full before-chain and dispatch run -- but this pipeline's
  provider is configured to reject `track()` calls for this exact event name,
  simulating a downstream outage. Core's own `console.warn` fires first
  (`typetrack: provider "checkout-events-warehouse" failed during "track()"...`),
  then `loggingMiddleware`'s `onError` fires with `source: "provider"` and
  `providerName: "checkout-events-warehouse"`. Crucially, the `after()` chain
  still runs afterward (`typetrack: [after] ...`, `[after] trace:start`,
  `[after] trace:end`) -- a provider rejection is swallowed inside dispatch,
  so it never stops the after-chain the way a *middleware* throw stops the
  before-chain.
