Notes on what's happening above, per step:
- Step 1: `createAnalytics({ plugins: [autoErrors(), autoWebVitals(),
  autoPerformance()] })` is constructed against a stubbed browser
  environment extended with a stub `PerformanceObserver` and
  `performance.getEntriesByType`. All three plugins are purely
  listener-registering at setup -- zero provider calls happen before any
  simulated event/entry is fed in.
- Step 2: a simulated `window` `"error"` event (as a real uncaught
  `TypeError` thrown deep in application code would produce) is tracked as
  `"Error Occurred"` with `message`/`filename`/`lineno`/`colno`/`stack`.
- Step 3: a simulated `unhandledrejection` whose `reason` is a plain string
  (`"Network request timed out"`, not an `Error` instance -- e.g. a
  hand-rolled `Promise.reject("...")` somewhere in application code) is
  tracked as `"Unhandled Rejection"` with that exact string as `reason` --
  `autoErrors()`'s `computeRejectionReason` only special-cases real `Error`
  instances (extracting `.message`); anything else is coerced via
  `String(reason)`.
- Step 4: three `"Web Vital Measured"` events, one per vital, deliberately
  chosen to land in a different rating bucket each: FCP at `1200`ms is
  `"good"` (<=1800ms), LCP at `4200`ms (the latest of two fed candidates --
  only the latest LCP value is ever kept) is `"poor"` (>4000ms), and CLS's
  accumulated total of `0.07 + 0.08` (a third, `0.5`-magnitude entry is fed
  with `hadRecentInput: true` and correctly excluded from the total -- e.g.
  a layout shift caused by the visitor's own click, not a surprise reflow)
  is `"needs-improvement"` (>0.1, <=0.25). LCP and CLS both finalize on the
  same single `visibilitychange -> "hidden"` event (the standard
  recommended finalization pattern); FCP had already fired immediately on
  its own first entry, no finalization needed.
- Step 5: a fake Navigation Timing entry is registered, then the `"load"`
  event fires -- `autoPerformance()` reads
  `performance.getEntriesByType("navigation")[0]` at that point and reports
  the computed duration fields (`ttfb`/`domContentLoaded`/`loadComplete`/
  `dnsMs`/`tcpMs`/`requestMs`/`responseMs`) as `"Page Performance Measured"`.
- Step 6: `analytics.destroy()` tears down `autoErrors()`'s two listeners
  (`error`/`unhandledrejection`) -- a further simulated error and rejection
  afterward produce exactly zero additional provider calls. `autoWebVitals()`
  and `autoPerformance()` have nothing further to tear down by this point in
  the flow: `autoWebVitals()`'s LCP/CLS already finalized in Step 4 (its FCP
  observer had already disconnected itself even earlier, right after its
  one-shot report), and `autoPerformance()` already fired its one-shot
  measurement in Step 5 -- see the Production notes below for why this is a
  documented limitation, not a bug this example works around.
