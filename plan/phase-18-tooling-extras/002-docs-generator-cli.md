# 002 -- `typetrack docs`: Markdown event catalog generator

## Context

Read `plan/phase-18-tooling-extras/BRIEF.md`'s Design decisions 2 and 6
first. Depends on issue 001 (`buildEventJsonSchemas()`,
`src/devServer/schemaExport.ts`, and the generalized `COMMANDS` table in
`src/cli/index.ts`) -- do not start this issue until 001 has landed.

This is the "documentation generator" from `plan/ROADMAP.md`'s Phase 18
line: renders a real app's `typetrack.config.ts` event schemas as a
Markdown event catalog (event name, payload shape, required/optional
properties, types) -- a human-readable artifact a team can check into its
own repo next to (or generated fresh from) its tracking plan. Not a
TypeDoc-style source-code API reference -- see BRIEF.md's "Research
grounding" for why that's explicitly not this issue's scope.

## Scope of this issue

### 1. `src/devServer/eventCatalog.ts` (new file): JSON Schema → Markdown

```ts
export function renderEventCatalog(eventJsonSchemas: EventJsonSchemas): string;
```

Pure function, no I/O. Input is issue 001's `EventJsonSchemas` (`{ events:
Record<string, unknown> }`, where each value is a `z.toJSONSchema()`
output). Output is a single Markdown document:

- A top-level `# Event Catalog` heading and a one-line generated-by note
  (e.g. `_Generated by \`typetrack docs\`._`) so a reader knows this file
  is derived, not hand-authored.
- Zero events (`events` is `{}`): a short "No event schemas found." body
  instead of an empty document -- this is a valid, non-error state (an app
  may have zero or partial schemas; `SchemaMap` entries are optional per
  `src/schema.ts`) and must render as clearly-empty output, not a blank
  file that looks broken.
- One `## {eventName}` section per event, in the input object's own key
  order (do not re-sort -- `Object.entries()` order matches config
  declaration order, which is the more useful reading order for a human
  tracking plan).
- For an event whose JSON Schema has no `properties` (covers both a
  no-payload event, e.g. `z.undefined()`, and any schema type whose JSON
  Schema representation has nothing to enumerate): a single line, `_No
  payload._`, no table.
- For an event with `properties`: a Markdown table with columns `Property`,
  `Type`, `Required`, `Description`. `Type` comes from the property's JSON
  Schema `type` field (fall back to `"unknown"` if absent -- e.g. a `oneOf`/
  `anyOf`-shaped union has no single top-level `type`; rendering the raw
  literal string `"unknown"` rather than throwing keeps this generator
  total over every valid Zod schema shape, matching the "never throws on
  well-formed input" bar the rest of this codebase holds itself to).
  `Required` is `Yes`/`No` based on whether the property name appears in
  the schema's top-level `required` array (absent array = every property
  optional = `No` for all). `Description` comes from the property's JSON
  Schema `description` field when present (populated when a config author
  writes `z.string().describe("...")`), else an empty table cell -- do not
  invent a placeholder string.
- Escape any literal `|` character inside a rendered type/description
  string (replace with `\|`) so it can never break the table's column
  structure.

### 2. `src/devServer/index.ts`: export

Add `export { renderEventCatalog } from "./eventCatalog";`.

### 3. `src/cli/docs.ts` (new file): the command

```ts
export interface RunDocsCommandOptions {
  cwd?: string;
}

export async function runDocsCommand(argv: string[], options?: RunDocsCommandOptions): Promise<number>;
```

Structurally identical to issue 001's `runSchemaCommand` (same config
resolution/loading/error-handling conventions -- reuse
`resolveConfigPath`/`loadConfig`/`ConfigLoadError` the same way), except:

- Flags: `--config <path>`, `--out <path>` (default when omitted:
  `EVENTS.md` in `cwd` -- unlike `schema`, this command always writes a
  file by default rather than defaulting to stdout, since a Markdown
  catalog is meant to be checked in/reviewed as a file, not piped;
  `--out -` writes to stdout instead, for scripting).
- Pipeline: `loadConfig` → `buildEventJsonSchemas` (issue 001) →
  `renderEventCatalog` (this issue) → write.
- Same "no config found" (exit 1) and `ConfigLoadError` (exit 1) handling
  as `runSchemaCommand`.
- Success: `✓ event catalog written to ${path}` to stdout (or, for
  `--out -`, the Markdown itself to stdout with no extra confirmation
  line, matching `schema`'s stdout-mode convention), exit 0.

Add a new `src/cli/docsArgs.ts` mirroring `schemaArgs.ts`'s
`parseSchemaArgs` shape (`parseDocsArgs`, same known-flags/`CliArgError`
pattern; reuse `CliArgError` from `./args`), with `--out`'s default of
`EVENTS.md` applied inside `runDocsCommand` (not baked into the parser, so
the parser's `ParsedDocsArgs.outPath` stays `string | undefined` like
`schemaArgs`'s does).

### 4. `src/cli/index.ts`: register the command

Add a `docs` entry to the `COMMANDS` table issue 001 introduced:

```ts
docs: {
  usage: "typetrack docs [--config <path>] [--out <path>]",
  run: async (argv) => (await import("./docs")).runDocsCommand(argv),
},
```

## Testing

- `src/devServer/eventCatalog.test.ts`: unit tests for
  `renderEventCatalog` -- empty input, single no-payload event, single
  event with required + optional properties (assert `Required` column
  values), a property with `.describe()` set vs. unset, a `|`-containing
  description is escaped, multiple events preserve input key order.
- `src/cli/docsArgs.test.ts`: mirrors `schemaArgs.test.ts`.
- `src/cli/docs.test.ts` / `docs.integration.test.ts`: mirrors
  `schema.test.ts`/`schema.integration.test.ts` (no config, malformed
  config, default `EVENTS.md` output path, explicit `--out`, `--out -`
  stdout mode).

## Out of scope

Any change to `typetrack schema`'s behavior (issue 001, already landed).
Rendering to any format other than Markdown (e.g. HTML, PDF) -- not asked
for by `plan/ROADMAP.md`.
